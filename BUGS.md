# Отчёт о тестировании Lab2 (консольный поиск по Википедии)

Дата: 2026-11-09
Окружение: Linux, OpenJDK 21.0.12, Maven Wrapper 3.9.11, Gson 2.13.1.
Сборка: `./mvnw clean package`
Запуск: `java -jar target/Lab2-1.0-SNAPSHOT.jar`

Тестирование проводилось тремя способами:

- реальные запросы к `ru.wikipedia.org` через CLI (ввод через pipe);
- офлайн-стенд на Java: напрямую вызывались `Parser`, `Main.showTotalHits`, `Main.getChoice`, `Main.errorResponse`;
- mock-сервер на localhost и HTTP-прокси для проверки таймаутов и сетевых ошибок.

Всего проверено: обычные/пустые/длинные/спецсимвольные запросы, кириллица, эмодзи, EOF, неверный выбор, границы выбора, битый JSON, ошибки API, HTTP 200/414/429, обрыв сети, зависший сокет.

## P0 — падения и потеря управления

### B1. EOF на приглашении запроса роняет программу

`Main.java:18`, `scan.nextLine()` при закрытом stdin бросает `NoSuchElementException`. Исключение нигде не ловится.

Воспроизведение:

```bash
printf '' | java -jar target/Lab2-1.0-SNAPSHOT.jar
```

Фактически:

```
Введите запрос: Exception in thread "main" java.util.NoSuchElementException: No line found
    at java.base/java.util.Scanner.nextLine(Scanner.java:1660)
    at Main.main(Main.java:18)
```

Ожидаемо: штатный выход (как при `exit`).

---

### B2. Выбор `0` принимается и роняет программу

`Main.getChoice` проверяет `choice < 0 || choice > max` (`Main.java:94`), то есть `0` считается допустимым. Затем `Parser.getPageId(0)` делает `elements.get(-1)` (`Parser.java:65`).

Воспроизведение:

```bash
printf 'test\n0\n' | java -jar target/Lab2-1.0-SNAPSHOT.jar
```

Фактически:

```
Выберите нужный вам вариант: Exception in thread "main" java.lang.IndexOutOfBoundsException: Index -1 out of bounds for length 10
    at com.google.gson.JsonArray.get(JsonArray.java:232)
    at Parser.getPageId(Parser.java:65)
    at Main.main(Main.java:35)
```

При этом сообщение валидации само рекламирует диапазон `[0, max]` (`Main.java:95`), то есть 0 выглядит разрешённым.

Ожидаемо: варианты нумеруются с 1, диапазон должен быть `[1, max]`; `0` — ошибка ввода.

---

### B3. EOF на приглашении выбора роняет программу

`Main.java:81`, `scan.nextLine()` в `getChoice` при EOF бросает `NoSuchElementException`.

Воспроизведение:

```bash
printf 'test\n' | java -jar target/Lab2-1.0-SNAPSHOT.jar
```

После вывода результатов и приглашения выбора программа падает с тем же стектрейсом `NoSuchElementException` (строка `Main.java:81`).

Ожидаемо: корректный выход.

---

### B4. Runtime-исключения парсера не ловятся

`Main` ловит только `IOException` (`Main.java:36`). `Parser` же при неожиданном ответе бросает runtime-исключения. Проверено офлайн-стендом:

| Вход | Исключение |
|---|---|
| `{not json` (например, HTML captive portal) | `JsonSyntaxException` |
| пустой поток | `IllegalStateException: Not a JSON Object: null` |
| `[]` | `IllegalStateException: Not a JSON Object: []` |
| `null` | `IllegalStateException: Not a JSON Object: null` |
| `{"query":{"search":null}}` | `ClassCastException: JsonNull cannot be cast to JsonArray` |
| `{"query":{"search":[42]}}` | `IllegalStateException: Not a JSON Object: 42` |
| элемент без `title` | `NullPointerException` в `getResults` |
| элемент без `pageid` | `NullPointerException` в `getPageId` |

То есть любой нестандартный ответ (прокси-заглушка, captive portal, изменившийся API, битый ответ) гарантированно роняет приложение стектрейсом.

Ожидаемо: `Parser` должен валидировать структуру и оборачивать всё в `IOException` (или `Main` должен ловить `RuntimeException` и печатать понятное сообщение).

## P1 — функциональные баги

### B5. `getPageId` без проверки границ

`Parser.java:64-65`:

```java
public String getPageId(int pos) {
    return elements.get(pos - 1).getAsJsonObject().get("pageid").toString();
}
```

`getPageId(0)` → `IndexOutOfBoundsException` (индекс `-1`), `getPageId(-1)` → индекс `-2`, `getPageId(size+1)` → индекс `size`. Сейчас частично прикрыто проверкой в `Main`, но сама проверка пропускает `0` (см. B2). Метод должен сам валидировать `1 <= pos <= size`.

---

### B6. «Показать больше вариантов» — мёртвый код

`Requester.java:19` не передаёт `srlimit`, поэтому API отдаёт дефолтные 10 результатов. Проверка через API:

```
GET .../w/api.php?action=query&list=search&utf8=&format=json&srsearch=test&srlimit=10
HTTP 200
totalhits = 7646
returned  = 10
continue  = {'sroffset': 10, 'continue': '-||'}
```

`showTotalHits` спрашивает «Показать больше?» только если `list.size() > 10` (`Main.java:46-49`), а `list.size()` всегда ≤ 10. Поэтому:

- вопрос никогда не задаётся;
- результаты после 10-го недоступны;
- код `Main.java:51-63` фактически недостижим на реальном API;
- параметры `continue`/`sroffset` игнорируются, пагинации нет.

Ожидаемо: либо явно запрашивать `srlimit` больше 10 и/или реализовать догрузку по `continue`, либо убрать мёртвую ветку.

---

### B7. «Было найдено N совпадений» показывает не то число

`Main.java:29` печатает `list.size()`, то есть максимум 10, а не `query.searchinfo.totalhits`.

Пример: реальный запрос `test` — `totalhits=7646`, приложение пишет:

```
Было найдено 10 совпадений.
```

Ожидаемо: показывать общее число найденных статей (`totalhits`) и, если показывается только страница, уточнять «показаны первые 10 из 7646».

---

### B8. `scan.next()` оставляет перевод строки и ломает следующий ввод

`Main.java:54`: `choice = scan.next().charAt(0);` читает токен, но не строку. После ответа `Y` в буфере остаётся `\n`, и следующий `getChoice` (`Main.java:81`) делает `nextLine()` и получает пустую строку.

Воспроизведение на офлайн-стенде: список из 15 элементов, ввод `Y\n1\n`:

```
Показать больше вариантов?[Y/n]:
...
Выберите нужный вам вариант: Необходимо ввести цифры, а не любые иные символы.
Выберите нужный вам вариант: choice=1
```

То есть после «показать больше» пользователь всегда получает ложную ошибку и должен вводить число ещё раз. Сейчас баг скрыт, потому что ветка недостижима (B6), но проявится при исправлении B6.

Ожидаемо: использовать `nextLine().trim()` и для вопроса, и для выбора.

---

### B9. Вопрос `[Y/n]` обрабатывается неправильно

`Main.java:52-55` принимает только ровно `'Y'` и ровно `'n'`.

Проверено:

- `y` → цикл повторяет вопрос, нужно ввести `Y`;
- `N` → цикл повторяет вопрос, нужно ввести `n`;
- пустой Enter → `next()` пропускает пустую строку и ждёт следующий токен, хотя `[Y/n]` подразумевает Y по умолчанию;
- EOF на вопросe → `NoSuchElementException` (не ловится).

Ожидаемо: `equalsIgnoreCase`, пустой ввод = `Y`, EOF = корректный выход.

---

### B10. `exit` работает только в точном виде

`Main.java:19`: `search.equals("exit")`. Ввод `Exit`, `EXIT`, ` exit `, `exit ` уходит в Википедию как поисковый запрос.

Проверено:

```
запрос [Exit]  -> Было найдено 10 совпадений. 1) "Exit" ...
запрос [ exit ] -> Было найдено 10 совпадений. ...
запрос [exit ]  -> Было найдено 10 совпадений. ...
```

В `getChoice` (`Main.java:83`) тоже только точный `exit`; `Exit`/`EXIT` дают «Необходимо ввести цифры». Поведение выхода непоследовательно между приглашениями.

Ожидаемо: `input.trim().equalsIgnoreCase("exit")` (и, возможно, отдельная команда `/exit`).

---

### B11. Заголовки печатаются в JSON-виде

`Parser.java:58`:

```java
temp.add(el.get("title").toString());
```

`toString()` возвращает JSON-представление строки. В консоли:

```
1) "Test"
2) ".test"
...
10) "C&C"
```

Для заголовков с кавычками/слешами вывод ещё хуже. Офлайн-проверка для `A "q" & <b> \ x`:

```
"A \"q\" & <b> \\ x"
```

То есть пользователь видит экранированные кавычки и `\\` вместо нормального текста. Нужно `getAsString()`.

`Parser.java:65` аналогично использует `toString()` для `pageid`: для числового id это ещё работает, но если API вернёт строковый id, в URL попадёт `curid="42"` с кавычками.

---

### B12. `title:null` и отсутствующие поля

Офлайн-проверено:

- `{"title":null,"pageid":1}` → в списке отображается строка `null` (не падение, но мусор);
- элемент без `title` → `NullPointerException`;
- элемент без `pageid` → `NullPointerException` при выборе.

Для реального API это маловероятно, но парсер не должен полагаться на удачу. Нужна проверка `hasNonNull`/типов и понятная ошибка.

## P2 — устойчивость и UX

### B13. 429 обрабатывается только сообщением

При серии быстрых запросов Википедия реально вернула 429. Приложение вывело:

```
Слишком много запросов. Подождите немного и попробуйте снова.
```

Это лучше, чем падение, но:

- заголовок `Retry-After` не читается;
- автоматического retry/backoff нет;
- пользователь не знает, сколько ждать;
- следующий запрос сразу уходит снова и снова получает 429.

Ожидаемо: пауза по `Retry-After` или экспоненциальный backoff с ограничением попыток.

---

### B14. Нет локальной валидации запроса

Проверено:

| Ввод | Поведение |
|---|---|
| пустая строка | HTTP 200 + `error`: `The "srsearch" parameter must be set.` → сообщение «Не удалось получить данные: Ошибка API: ...» |
| строка из пробелов | HTTP 200, 0 результатов |
| 2000 символов | `error`: `Search request is longer than the maximum allowed length. (Actual: 2000; allowed: 300)` → сообщение об ошибке |
| 9000 символов | HTTP 414 → «Запрос слишком длинный для сервера.» |

Падений нет, но пустой/пробельный запрос лучше отсекать до сети, а лимит 300 символов проверять локально с нормальным русским сообщением. Сейчас пользователь получает английский текст API.

---

### B15. `disconnect()` пропускается на `continue` и `break`

`Main.java:30`: `if (list.isEmpty()) continue;` — переход на следующую итерацию минует `req.disconnect()` (`Main.java:42`).
`Main.java:33`: `if (choice == -1) break;` — выход из цикла тоже минует `disconnect()`.

Следующий `makeConnection()` начинается с `disconnect()` (`Requester.java:16`), поэтому бесконечной утечки нет, но соединение/поток висят до следующего запроса или до завершения процесса. Правильнее `try/finally` вокруг обработки запроса.

---

### B16. Сетевые ошибки теряют причину

`Requester.makeConnection()` (`Requester.java:28-33`) возвращает `-1` и для `MalformedURLException`, и для любого `IOException`, не сохраняя исключение. `Main.errorResponse(-1)` всегда пишет «Проверьте подключение к интернету».

Проверено mock-прокси:

- закрытый порт → `-1`, сообщение про интернет (корректно);
- зависший сокет → через ~11 секунд `-1`, сообщение про интернет (timeout работает, но причину не видно);
- прокси, ответивший 500 на `CONNECT`, тоже превращается в `-1` и «проверьте интернет», хотя проблема не в интернете.

Ожидаемо: хранить последнее исключение/код и выводить `e.getMessage()` или хотя бы класс ошибки.

---

### B17. Кодировка консоли не задана явно

`Main.java:14`: `new Scanner(System.in)` и `System.out` используют кодировку платформы. На этой машине локаль UTF-8, поэтому кириллица и эмодзи работают. На системе с другой кодировкой ввод/вывод сломается.

Ожидаемо: `new Scanner(new InputStreamReader(System.in, StandardCharsets.UTF_8))` и `PrintStream(..., true, StandardCharsets.UTF_8)`.

## P3 — мелочи и косметика

### B18. `getChoice`: trim и переполнение

- `" 1"` → «Необходимо ввести цифры...» (пробел не обрезается);
- `"2147483648"` → тоже «введите цифры», хотя это цифры, просто число не влезает в `int`;
- `"+1"`, `"01"` принимаются;
- `"00"` превращается в `0` и приводит к падению (B2).

Ожидаемо: `trim()`, `Long.parseLong`, проверка диапазона `[1, max]`, отдельное сообщение про слишком большое число.

### B19. Опечатки и грамматика

- `Main.java:95`: «Введеного вами числа нет в допустимом диапозоне[0, %d]» → «Введённого вами числа нет в допустимом диапазоне [1, %d]».
- `Main.java:118`: «При открытие следующей ссылки...» → «При открытии следующей ссылки...».
- `Main.java:53`: «Показать больше вариантов?[Y/n]: » → нужен пробел перед `[`.
- `Main.java:29`: «1 совпадений» → нужна форма «1 совпадение» / «2 совпадения» / «5 совпадений».

### B20. Качество кода

- `new URL(...)` в `Requester.java:20` deprecated в Java 20+ (предупреждение компилятора).
- `Scanner` в `Main` не закрывается (для stdin не критично, но в статическом анализе будет замечание).
- `BufferedReader` в `Parser.java:19-27` не в try-with-resources: при исключении во время чтения поток не закроется.
- Поле `Parser.json` (`Parser.java:15`) используется только внутри конструктора, можно сделать локальной переменной.
- В `Main.java:4` импортирован `java.util.List`, но в `Main.java:27` всё равно используется полное имя `java.util.List`.
- `handle` ошибок `openPage` ловит `Exception` и теряет причину (`Main.java:117-118`).

### B21. Документация и сборка

- `README.md` содержит только эмодзи, инструкции по Maven-сборке отсутствуют.
- `build.sh` остался вторым способом сборки: он жёстко завязан на `~/.m2` и `out/`, дублирует Maven и может разойтись с `pom.xml`.
- В Maven-проекте нет ни одного теста (`src/test` отсутствует), поэтому `./mvnw test` ничего не проверяет.

## Что работает корректно (проверено)

- `./mvnw clean package` собирает исполняемый fat-jar `target/Lab2-1.0-SNAPSHOT.jar`; `java -jar` запускается.
- `./mvnw` работает без системного Maven (wrapper сам скачивает 3.9.11 в `~/.m2/wrapper`).
- Обычные запросы: `test`, `C++`, кириллица, эмодзи, `a&b=c?d#e`, кавычки, `%`, `+`.
- Ноль результатов: сообщение «Было найдено 0 совпадений.» и возврат к приглашению без падения.
- Ошибка API для пустого запроса обрабатывается через `error.info` (B14 — только UX).
- HTTP 414 и 429 выводят понятные сообщения, без падения.
- Отказ сети (закрытый порт) → `-1` и сообщение, без падения.
- `connectTimeout`/`readTimeout` реально работают: зависший прокси дал отказ примерно через 11 секунд.
- Валидация выбора: отрицательные числа, `11` при максимуме 10 и нецифровой ввод отклоняются и запрашиваются повторно.
- `exit` из главного приглашения и из приглашения выбора (в точном нижнем регистре) работает.
- `openPage` в headless-окружении не роняет программу: печатает «При открытие следующей ссылки произошла ошибка: ...».
- Для числового `pageid` URL формируется правильно: `https://ru.wikipedia.org/w/index.php?curid=819811` (без кавычек).
- `Parser` корректно обрабатывает валидный ответ, пустой `search[]`, отсутствие `search` и объект `error`.
